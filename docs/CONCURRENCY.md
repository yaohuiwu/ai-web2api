# 并发与锁：只为**可用性 + 正确性**

> 原则：**不复杂化**。不做优先级、不做公平调度。锁只解决两件事：
> ① 同一页面不被两个请求同时操作（正确性）；② 请求多的时候不把服务拖死（可用性）。

## 1. 三层资源与各自的对策

| 层 | 冲突 | 对策 |
|---|---|---|
| **会话页**（thread_id） | 页面只有一个输入框：两个请求同时打字会互相覆盖 | `ThreadSession.lock`（每会话一把） |
| **Provider** | 同站点的多个页面同时打字/抓取：CPU 争抢 + **风控风险** | `SerialGate`（每 provider 一个闸门，默认 **1 并发**） |
| **浏览器 / 整机** | 页面数、实时画面截图抢 CPU | `server.max_threads` 限会话数；实时画面在有请求在跑**或有人排队**时自动降帧 |

**锁序固定：`会话锁 → 闸门`**（任何入口都按这个顺序，避免死锁）。
thread 模式此前只拿会话锁、绕过闸门 → 已统一（否则同 provider 多会话会并行，`busy` 也不准）。

## 2. 队列预算（要短）

```yaml
providers:
  <name>:
    queue:
      max_size: 3        # 排队人数上限（含正在跑的）→ 超出 429
      timeout: 30        # 等待上限（秒）→ 429
      max_inflight: 1    # 同时几个请求在跑
```
- **超限/超时一律 429**，让客户端自己重试——排队干等对谁都没好处；
- `max_inflight` 默认 **1**：最安全、最省 CPU、风控风险最低。
  需要"不同会话并行"时才调到 2–3，代价是**同一站点并发↑ → 被限流/风控概率↑**。

## 3. 不做优先级（明确记录）

- 网页生成**不可抢占**：正在跑的那次请求没法中途让位，所以"优先级"只在*排队*时有效，
  收益小、复杂度高（两套队列、UI/API 标记、行为分叉）；
- Playground 只是体验用途：它本来就该"忙的时候自己重试"，而不是靠优先级插队。

## 4. 其它入口

| 入口 | 行为 |
|---|---|
| 画面交互 `/admin/{p}/input` | 目标会话**正在生成** → **409**（提示稍后再试）；否则串行执行（每 provider 一把输入锁） |
| 实时画面 | `busy` **或** 有人排队 → 自动降帧（把 CPU 让给生成）；screencast 每页一份归属，冲突则回退定时截图 |
| 登录/维护 | 与请求闸门分开考虑，避免长时间占位把用户请求饿死 |

## 5. 可观测

- `/admin/status` → 每个 provider 的 `queue: {running, waiting, max_waiters, avg_wait_ms, recent_waits_ms}`；
- 请求时间线 → **`queued_ms`**（等锁时长）：把"排队慢"和"生成慢"分开看
  （`docker compose logs | grep '\[timeline\]'`）。

## 6. 测试（`tests/test_serial_gate.py`）

1. 同 provider **串行 + FIFO**；
2. 队列**短**：超出上限立刻 429；
3. 等待**超时**立刻 429，且**不留幽灵等待者**；
4. **取消**（客户端断流）→ 执行权释放、无死锁；
5. `max_inflight=2` 时可并行（可选开关）；
6. `run/run_iter` 的等待时长回调 + `stats()`。
