# 文本捕获保真度（Text Fidelity）

> 目的：用**可复现的度量**证明"我们返回的正文 == 页面上真实可见的文本"，
> 并在回归时**自动告警**（覆盖率下降/正文混入思考）。
> 测试：`tests/test_text_fidelity.py`（`-m live`，需服务已启动且已登录）；脚本：`scripts/text_fidelity.sh`。

## 1. 度量方法（尽量独立）

1. 通过 `/v1/chat/completions` 发一条用例消息（带 `thread_id`，`deep_think: true`）；
2. 用 `/admin/threads?q=<thread_id>` 找到该会话的页面 URL；
3. **另开一个 Playwright** 打开该会话页，**只读 DOM 的 `innerText`**
   （刻意**不用**我们的 markdown 提取器，避免"自己校验自己"）；
4. 比对：
   - **句子覆盖率** = 页面句子中能在我们正文里找到的比例（归一化：只留字母/数字/汉字，忽略 markdown 标记）
   - **思考污染** = 正文里是否出现推理特征文本（`正在思考中`、`思考已完成`、以 `The user says` / `We need` 开头…）
   - **长度** = 正文/思考字数（仅作参考，模型每次输出长度不同）

判定阈值：**覆盖率 ≥ 0.95 且无思考污染** → 通过。

### 为什么"思考污染"用特征词，而不是"与思考文本重合"

首次跑时用"正文与思考文本重合即视为污染"，**deepseek/代码块用例误报**：
写代码类任务里，模型**在思考中草拟的代码与最终正文本来就相同**（重合是正常的）。
真实 bug 的表现是正文**以推理口吻开头**（实测 Kimi 曾返回
`The user says "再给生成一次" …` / `正在思考中 用户说…`），因此改用特征词判据。

## 2. 实测结果（2026-09-22，容器内 headful，服务已登录）

| provider | 用例 | 耗时 | 正文 | 思考 | 句子覆盖率 | 思考污染 |
|---|---|---|---|---|---|---|
| **DeepSeek** | 长文本 / 多段列表 | 7.4s | 852 字 | 1705 字 | **1.00** | 无 |
| **DeepSeek** | 代码块（Python + 注释） | 4.2s | 674 字 | 783 字 | **1.00** | 无 |
| **DeepSeek** | Markdown 表格（3 列） | 2.8s | 226 字 | 532 字 | **1.00** | 无 |
| **ChatGPT** | 长文本 / 多段列表 | 13.7s | 316 字 | — | **1.00** | 无 |
| **ChatGPT** | 代码块（Python + 注释） | 12.7s | 528 字 | — | **1.00** | 无 |
| **ChatGPT** | Markdown 表格（3 列） | 8.3s | 151 字 | — | **1.00** | 无 |
| **Kimi** | × 3 用例 | — | — | — | ⛔ 未完成（`504`→`429`） | — |

**结论：DeepSeek 与 ChatGPT 共 6/6 用例，句子覆盖率 1.00、零思考污染** —— 包含长文本、代码块、表格、以及"思考 + 正文"并存的情形。
（另有一次更早的运行同样是 6/6 覆盖率 1.00；正文长度每次不同属正常。）

### Kimi 为什么没跑完（**不是抓取问题**）

1. 首个请求 `504`（Kimi 侧排队超时），它**占住了该 provider 的串行闸门 180s**；
2. 后续两个请求等不到闸门 → 按设计返回 **`429 queue full`**；
3. 该账号是 **Free 档**且处于高峰排队（页面提示「和Kimi聊天的人太多了，订阅会员可进入优先队列」）。

排队放开时 Kimi 的文本链路**已验证正常**（正文/思考分离、无 UI 文案：实测 `content='收到'`，thinking 68 字）。
测试对该情形**自动 skip**，不会误报失败。

## 3. 接入日常流程（告警钩子）

```bash
./scripts/text_fidelity.sh                 # 跑全部 provider（Kimi 排队时自动 skip）
./scripts/text_fidelity.sh deepseek        # 只跑一个 provider（~50s）
```

- 结果同时写入 `reports/text_fidelity-<日期>.log`，结构化历史追加到 `reports/text_fidelity.jsonl`
  （每用例一行：时间/provider/用例/覆盖率/长度/污染），便于观察**趋势**；
- **退出码 = pytest 结果** → 直接给 cron/监控用：
  ```cron
  0 9 * * * cd /path/to/ai-web2api && ./scripts/text_fidelity.sh >> reports/cron.log 2>&1
  ```
  非 0 即代表"有用例不达标"（覆盖率 < 0.95 或正文混入思考特征文本）。
- 为什么不做成 CI：live 用例需要**真实登录态 + 真实浏览器**，GitHub Actions 无法满足；请在本机/自建机跑。

## 4. 已知边界

- **覆盖率**是"页面句子能否在正文里找到"，对**同一句话被拆成多处**的排版不敏感（这是刻意的：我们关心"内容有没有丢"）；
- 站点**过程性文本**（如工具调用前的过渡句"路线数据已确认。现在把这套…"）属于页面上模型真实可见文字，
  默认**保留**在正文里（删除有误伤风险）；
- 交互组件（iframe widget）的内容不属于"文本正文"，另见 `docs/WIDGET_CAPTURE.md`（已实现按配置捕获）。
