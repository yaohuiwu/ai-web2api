## 1. 现状：两条通道

| 通道 | 用在哪 | 做法 |
|---|---|---|
| **DOM 轮询 + diff**（主） | 所有 provider | Playwright 轮询响应容器 → `extractor` 把 HTML 转 Markdown → 前缀 diff 出增量 |
| **页面内 JS 钩子（网络监听）** | 目前只有 DeepSeek（`network.url_pattern` + `_parse_sse_snapshot`） | `add_init_script` 注入 XHR 钩子，把 `responseText` 存到全局量 → 解析 SSE 里的 JSON 字段 |
| **观测型旁听**（本次新增，仅时序） | Gemini（`network.observe`） | Playwright `page.on("response")`，只记 **status / 响应头时间 / 结束时间**，**不解析内容** |

## 2. 今天的实测证据：DOM 通道的失败**都是同一批"类"问题**

| # | 现象（真实事故） | 根因类别 |
|---|---|---|
| 1 | Kimi 只拿到回答第一段（工具前那段），后半段+文件卡丢 | **回答被拆成多个容器**，只取了"新增的第一个" |
| 2 | Kimi 正文里混进 `The user says…` / `正在思考中…` | **思考与正文同容器**，仅靠 CSS `:not()` 不可靠 |
| 3 | Kimi "思考中 Ns" 每秒跳动 → 稳定计数被反复清零 → 180s 超时（答案其实已生成） | **用"整体稳定"当结束判据**，思考区在动 |
| 4 | 豆包 `.md-box-root` **同时匹配用户提问** → 差点把"问题"当"回答" | **容器不区分角色** |
| 5 | 豆包/GLM/Kimi 长表格只拿到表头+碎片（覆盖率 0.08） | **重渲染把内容打断**（需缓冲 + 拼接） |
| 6 | ChatGPT 多次"点发送成功但消息没发出"；输入框留着原文 | **发送 ≠ 送达**（无送达确认） |
| 7 | ChatGPT 续聊变新会话（页面 2s 没渲染完就被判"恢复失败"） | **固定等待 vs 等就绪** |
| 8 | ChatGPT 逐字 diff 会丢内容（重渲染） | **diff 与重渲染不兼容** |
| 9 | 无效/限流时表现为"页面一直生成中"，只能等满 timeout | **无法区分"慢/排队/流卡住/我们没找到容器"** |

**已经修掉的**（今天）：`response_all_new` 拼接、按内容剔除思考、content/thinking **独立稳定计数**、
**超时兜底返回已生成内容**、role-aware 容器、缓冲(`stream_content: false`)、
**发送送达确认 + 关弹窗重发**、恢复时"等就绪"而非固定等待、**观测型旁听**（回答第 9 类）。

**结论**：DOM 通道**可用**（DeepSeek/ChatGPT/豆包 保真度 3/3、覆盖率 1.00），
但它的可靠性**依赖每个站点的"容器结构 + 角色语义"被正确配置**，
且**结束判定是启发式**（停止按钮 / 稳定窗口 / 最小等待）——今天的事故几乎都出在这两点上。

## 3. 备选方案对比

| 方案 | 文本从哪来 | 跨站通用性 | 结束判定 | 代价 / 风险 |
|---|---|---|---|---|
| **A. DOM 轮询 + diff（现状主路）** | 渲染后的 HTML | ✅ 通用（只依赖选择器） | ❌ 启发式（停止按钮/稳定） | 配置成本；易受重渲染/虚拟化/角色混淆影响（见 §2） |
| **B. 页面内 JS 钩子 + 解析响应（DeepSeek 在用）** | 站点原始响应 | ❌ 每站一套解析（＝逆向内部协议） | ✅ 明确（SSE close） | 站点改版即失效；注入需在页面加载前；**实测对 Gemini 完全抓不到**（钩子挂上后 0 请求被记录） |
| **C. CDP 侧读取响应体** | 同上 | ❌ 仍需逐站解析 | ✅ 明确 | 需 `Fetch`/`Network` 域与流式读取 API，复杂度高；仍绕不开"解析协议" |
| **D. 混合：网络当"控制信号"，DOM 当"文本源"（推荐探讨）** | DOM（不解析协议） | ✅ 通用 | ✅ **明确**（响应流开始/结束 → 告诉 DOM"可以定稿了"） | 需要 provider 声明一个 URL 规则；时序偶发不可用需回退（已有 fallback 架构） |
| **E. 官方 API** | 官方接口 | ✅ | ✅ | **最可靠**，但已不是"网页封装"（GLM/Gemini 这类受限站点长期就该走这条） |

### 为什么"要监听网络"这个直觉既有道理、又不能全做
- **有道理**：网络里有**真实、无噪声、无重渲染**的文本，且**天然有明确的开始/结束**（SSE `close` / 最后一块）。
  DOM 的所有事故（§2 的 1/2/3/5/6/8）在网络通道里基本不存在。
- **不能全做**：要用网络里的**文本**，就必须**解析每站的私有协议**（ChatGPT 是 JSON-Patch、Gemini 是长度前缀数组、DeepSeek 是 JSON SSE）——
  这正是项目原则里"**不做逆向内部 API**"的边界；而且实测**页面内钩子并不可靠**（Gemini 用例：钩子装上后 0 请求被记录，
  站点可能用 Service Worker/缓存引用规避）。**B/C 的收益随时间衰减（改版即失效），维护成本却持续。**

### 方案 D 具体长什么样（建议重点讨论）
把"**网络**"和"**DOM**"的职责切开，各用所长：

```
网络（Playwright 响应事件 / CDP）              DOM（选择器 + 提取器）
─────────────────────────────              ─────────────────────────
① 匹配到完成请求 → 标记"回复开始"        →  从这里开始轮询正文容器
② 响应 status / 响应头时间                  （不再依赖"容器计数增加"猜测开始）
③ 流结束（responseEnd / SSE close）      →  「定稿」：再等 1-2 拍取最终文本返回
④ 429 / 流长时间不结束（已实现）         →  直接给准确错误（限流 vs 长思考 vs 卡住）
```

收益（都是今天的事故 1/3/6/9）：
- **开始判定**：不再"猜"（等容器计数变化），由请求生命周期驱动 → 更快、更少误判；
- **结束判定**：不再依赖"停止按钮/稳定窗口"（事故 3 的根因），**延迟也更低**（现在 DeepSeek 3-9s 里有一部分是稳定窗口白等）；
- **失败可解释**：限流/长思考/卡住分得清（已落地一半）。

代价：
- 每个 provider 加一条 `network.url_pattern`（Gemini 已经加了：`…/StreamGenerate`；ChatGPT/豆包需要实测补上）；
- 有些站点/场景拿不到响应事件（Service Worker、跨域 iframe、页面跳转）→ **必须保留 DOM 回退**（现有架构已是"网络优先 + DOM 兜底"）；
- 仍然**不解析内容**（红线不变），所以不会引入"逆向维护负担"。

## 3.5 路线 1 落地：Provider 接入检查清单（**每次接入/改版后逐条过**）

| # | 检查项 | 为什么 |
|---|---|---|
| 1 | `response_container` 必须**只匹配助手侧** | 豆包 `.md-box-root` 同时匹配用户提问 → 会把"问题"当"回答" |
| 2 | `response_all_new: true`（多段/多容器站点） | Kimi/豆包实测回答被拆成多段，只取第一段 → 截断 |
| 3 | `stream_content: false`（重渲染严重的站点） | ChatGPT/豆包/Kimi 逐字 diff 会丢内容 |
| 4 | 思考与正文**同容器**时：按内容剔除思考（`_looks_like_thinking`） | Kimi 曾把 `The user says…` 当正文 |
| 5 | 有停止按钮时，**消失后仍要求 N 拍稳定**（`stop_settle_polls`，默认 2） | 按钮消失后最后一拍还没渲染完 → 长回答/表格被截断 |
| 6 | 发送后要**确认送达**（输入框清空 + 无生成迹象 → 重发一次） | ChatGPT/豆包实测"点发送成功但没发出" |
| 7 | 恢复会话要**等就绪**（等输入框出现）而非固定等待 | ChatGPT 2s 未渲染完 → 误判恢复失败、另开会话 |
| 8 | 改完跑 **`./scripts/text_fidelity.sh`**，覆盖率 < 0.95 或出现思考特征文本即不达标 | 用数据验证"页面可见文本 == 我们返回的正文" |

## 4. 我建议的路线（供你选）

**路线 1（保守，先做小改）**：继续 DOM，但把今天的经验固化：
- `response_all_new: true`、`stream_content: false`、role-aware 容器、**停止按钮消失后再等稳定**（补上"双确认"）；
- 保真度回归纳入日常（已有脚本）。
- 成本：小；风险：低；收益：把"已发生过的事故"挡在门外。

**路线 2（推荐，做 D）**：在路线 1 之上，把**开始/结束判定改为网络驱动**，DOM 只负责取文本。
- 成本：中（每 provider 一条规则 + 框架里一个"流生命周期 → 轮询状态"的桥接 + 回退 + 测试）；
- 风险：中低（保留 DOM 兜底，失败即回到今天的行为）；
- 收益：**结束判定更准、延迟更低、失败可解释**，且**不触碰协议解析**。

**路线 3（大改，不建议）**：按站点解析响应体（B/C）。收益被改版风险吃掉，且违背"不逆向"原则。
